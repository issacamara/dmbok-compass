## 1. Executive Summary

DMBOK Compass remains an access-controlled, corpus-grounded React/TypeScript application backed by a FastAPI modular monolith on Cloud Run.
LangChain replaces custom document loading, chunking, embedding, vector storage, retrieval, and generation inside the existing API and batch jobs.
Firebase Authentication, Firestore, Cloud Storage, Cloud Run Jobs, and the configured hosted providers remain the backing services.
Application code retains authorization, quotas, provenance enrichment, corpus lifecycle, evidence/refusal policy, citation validation, and privacy-safe response mapping.
A shared LangChain configuration/chain factory serves production requests and corpus-pinned evaluations; operational failures gain corrected HTTP status semantics.
A release manifest and durable decision bind the serving image, corpus, policies, dependencies and evaluation evidence; promotion rejects blocked or stale evidence.
Staged ingestion validates the serving chunk contract and proves candidate-filtered vector search readiness before publication.
Retrieval metrics, answer assessment and operational success are independent; explicit model output limits and content-free structured events make quality, latency and cost gates truthful.
Active and rollback source generations remain recoverable while referenced by a release.
Each selected change is an independently reviewable workstream behind shared candidate, retrieval, answer and configuration contracts; integration gates connect them before release.
Release still requires the existing quality, latency, cost, privacy, provider, publisher-risk, backup, and recovery evidence.

## 2. Business Context & Drivers

DMBOK Compass replaces manual searching of *DAMA-DMBOK, Second Edition* with evidence-backed lookup, comparison, synthesis, study support, and scenario guidance. The sponsor, product owner, administrator, evaluator, corpus owner, support owner, and release approver are currently the same person. Other actors are registration applicants, approved users, and hosted model providers.

In scope are public registration requests, verified email/password identity and administrator approval, a responsive English browser interface, corpus-only answers, page/section citations, request-scoped retrieval traces, configurable quotas, aggregate administration, offline ingestion of one searchable PDF, administrator JSON evaluation import, record validation, gold review, exploratory/release-eligible evaluation, daily backup, and documented recovery. The first release excludes anonymous access, more than 10 approved users, multiple corpora, saved conversations, feedback, MFA, native mobile applications, an admin PDF-upload interface, contractual uptime, and high-availability infrastructure.

The sponsor approved replacing all six RAG mechanisms with LangChain while preserving functionality. Functional equivalence means the same workflows, evidence outcomes, citation authority, quotas, fallback rules, and privacy behavior; nondeterministic model answers need not be byte-identical. LangChain supplies library integrations rather than another deployed service. It does not assume ownership of product policy, identity, domain repositories, or release decisions. A non-2xx status for an operational failure is a deliberate correction to the current HTTP contract, while retaining a safe error body.

The architecture reuses the current FastAPI/React codebase, ingestion/evaluation job entrypoints, domain contracts, Firebase, Firestore, Cloud Storage, infrastructure, and delivery workflows. Graphify's 2026-10-10 report/maps guided navigation; source and the current BRD working copy take precedence over older graph/document descriptions. The existing custom runnable wrappers do not implement the requested replacement. Sections 5–13 incorporate the architectural impact findings and the nine selected production-readiness risks.

The principal drivers remain grounding/citation quality, reproducible release decisions, non-retention of production interactions, the €5 GCP infrastructure constraint plus approved provider budget, and maintainability by one sponsor. Provider terms/capacity, publisher rights, PDF provenance, and LangChain/Firestore compatibility remain explicit validation gates. No infrastructure expansion or relaxation of acceptance thresholds is authorized by this migration.

## 4. Architecture Overview

At context level, applicants and approved users use the browser application; the administrator additionally manages users, quotas, evaluation imports/gold review, corpus maintenance, evaluations, and release decisions. At container level, Firebase Hosting serves the React SPA, the Cloud Run FastAPI monolith serves authenticated JSON APIs, and Cloud Run Jobs perform ingestion/evaluation. Firestore remains the application and vector store; Cloud Storage remains the immutable source/artifact repository. No new service, database product, agent runtime, or persistent interaction store is introduced.

Inside the existing Python processes, a shared validated factory creates native LangChain loading/splitting/embedding/vector and retrieval/generation compositions. Production resolves an immutable approved release manifest once per request, including its corpus binding; evaluation supplies the same candidate manifest before approval. The mutable `corpus_state/active` pointer is a publication record, not an independent serving authority. Application policies surround and participate in these chains, while LangChain integrations own the six RAG mechanisms.

The nine selected findings are separate modules and work items inside these containers. Evaluation authoring writes reviewed, corpus-bound gold data; scoring consumes a versioned run record and does not depend on the authoring UI. Dense retrieval remains the baseline; an optional lexical/fusion/rerank strategy implements the same retrieval result contract. Prompt assembly and citation checking consume immutable retrieved passages but have separate tests and release metrics. Typed answer outcomes and validated runtime settings are shared contracts, not reasons to combine the work into one deployment unit.

## 5. Component Design

### 5.1 Web Application

- **Purpose and responsibilities:** Retain registration/authentication, question entry, answer/citation/trace rendering, quota messages, administrator users/configuration, JSON import/reporting, gold review, and exploratory/release labels. Handle the corrected non-2xx operational-error status with the existing safe user message.
- **Classification:** **Reused.** Existing React screens and TypeScript contracts meet the UI boundary; no migration-specific user workflow is required.
- **Interfaces and data owned:** Firebase browser identity SDK and existing backend HTTPS JSON contracts; no authoritative durable state or saved conversations.
- **Technology:** React/Vite/TypeScript on Firebase Hosting. Validate core flows, mobile/desktop responsiveness, and basic WCAG 2.1 AA after the backend swap.
- **Selected-risk contract (R05/R17/R18):** The administrator can review imported support bindings and assess the actual output of a pinned evaluation run. The question view renders the bounded supporting excerpt attached to each cited claim, with page and section from the server; it shows an evidence refusal separately from a service failure. The browser does not decide citation validity or evaluation eligibility.

### 5.2 Backend API

### 7.1 Corpus schema, identity and lifecycle

The target native vector collection is `document_chunks_v2` (externally configured), with top-level `text`, `embedding` and `metadata`. The metadata map contains `corpus_version_id`, `chunk_id`, one-based `page`, `section`, `chunk_ordinal`, `content_hash`, source identity and schema version. Configure the native converter and validate the actual round trip: do not assume returned `Document.metadata` is automatically flattened. A small boundary mapping reconstructs application `DocumentChunk`/`RetrievedPassage`; internal vectors/library metadata do not leak into the API.

The target Firestore index combines `metadata.corpus_version_id` filtering with 768-dimensional `embedding` cosine search. This replaces the target access path, not the existing flat-field index in `document_chunks`; retain that legacy collection/index for the legacy revision. Use explicit document IDs. Validate missing fields, page/section attribution, metadata nesting, vector length and persisted content hashes before candidate readiness.

If R15 earns promotion, the ingestion job also creates a deterministic lexical index from the exact staged `chunk_id`/text set, stores it as an immutable Cloud Storage artifact and records corpus, tokenizer/algorithm version, chunk count and SHA-256 digest in the candidate manifest. Each API instance loads only the selected artifact into a bounded local cache and verifies its digest; it does not scan Firestore on every cold start. The dense-only strategy has no lexical artifact. A missing/mismatched artifact makes a selected hybrid strategy unready; it cannot silently change the ranking algorithm.

Keep source identity (bucket, object, immutable generation and digest) separate from the derived corpus identity. The derived fingerprint includes source identity, loader/parser version/configuration, normalization/provenance and overlong-chunk subdivision algorithms, splitter type/version/word units/700–70 settings, embedding model/dimensions/document/query tasks, and schema version. Derive chunk IDs from derived corpus version plus page/ordinal/subdivision ordinal. Existing source-only manifest IDs and the already-active early exit are insufficient when the same PDF is parsed/split/indexed differently; change the idempotency key with the derived identity. Never overwrite an active legacy chunk ID with changed text/vectors. Validate that every persisted chunk can round-trip through the serving `RetrievedPassage` contract; reject one that cannot be split within the allowed provenance and provider limits.

Create a staged corpus with expected page/chunk counts and manifest hashes. Library writes use bounded idempotent batches; retries resume against the same derived identity. After all batches persist, first verify stored counts, provenance, hashes and 768 dimensions. Then issue an actual vector query with a known candidate chunk embedding and a server-side `metadata.corpus_version_id` filter against the target collection/index. Require the returned candidate's identity/provenance and finite score to match the probe contract; retry only index propagation within a bounded deadline. Persist `complete` and `search_ready` as separate evidence with timestamps and collection/index identities. Neither proves retrieval quality. Ingestion marks a candidate ready for evaluation and does not switch the serving release. A release publisher uses transactional compare-and-set against the previously approved release reference; a concurrent publisher cannot supersede it accidentally. Failed ingestion leaves serving state untouched; clean abandoned staging data through an authenticated maintenance job.

The immutable `ReleaseManifest` binds API/frontend/job artifact digests, installed dependency lock digest, prompt and evidence-policy versions/hashes, configured model routes and output-token cap, collection/schema/index, derived corpus and source generation, retrieval settings, evaluation dataset/scorer versions and evidence IDs. Its approval decision records sponsor actor/time and accepted exceptions. Production resolves the approved release binding once per request and checks it against the running image; evaluation pins the candidate manifest explicitly. `corpus_state/active`, if retained for maintenance compatibility, must be updated by the publisher in the same transaction and checked against the release reference, never used alone to select serving data. Keep the previous valid release and its revision/index/data/source through rollback acceptance. Parser, splitting, normalization, vector or layout changes require a new staged rebuild; merely retaining the same embedding dimension does not prove data compatibility.

### 7.2 Interaction and evaluation data

Production questions, prompts, retrieved passages, generated answers, and request traces exist only in Cloud Run memory and the live HTTPS response. They are never written to Firestore, Cloud Storage, logs, analytics, traces, backups, or build artifacts. The request response contains the answer, evidence outcome, synthesis marker, citations, retrieved passages and preserved scores, selected model and attempts, optional raw model output, and retrieval/generation/total timing; the browser discards this state when the request/session lifecycle ends.

Evaluation questions are separate, administrator-authored non-user data. JSON import accepts only records with a non-empty question, one allowed category (`definitions`, `explanations`, `comparisons`, `study`, `scenarios`), an expected answer or rubric, and a supporting passage. Validation returns submitted, imported, and skipped counts plus each skipped record's index and reason. Valid records are staged under a new generation ID; zero-valid imports are rejected. After all valid records are durable, a Firestore transaction compares and switches the active-generation pointer and marks prior runs superseded for release-evidence queries. If validation or writing fails, the pointer and visible history do not change; orphaned staged records can be cleaned up later. Run launch resolves the active generation on the server, pins that ID and selected item IDs for the job, and checks the generation again before exposing results as current evidence.

Imported records can run immediately as `exploratory`. Administrator review approves or rejects gold annotations per record and persists the status. A report is labeled `release_evidence` only when its run is bound to the active generation with 30–50 approved gold items and the required evaluation coverage; the label does not imply that its metrics passed. The release-decision endpoint rechecks the active generation, gold count, coverage, and passing thresholds transactionally. Older generation runs remain version-bound for audit/reproduction of earlier decisions but are not presented as available evidence for the active dataset. This resolves FR-022's reproducibility requirement alongside FR-029's replacement requirement without confusing old results with current release readiness. Reports bind dataset, derived corpus, collection/schema, loader/splitter/provenance fingerprint, dependency lock/integration artifact, retrieval/evidence settings, embedding, prompt, effective provider/route/model, scorer and application image/configuration versions. Evaluation datasets, annotations, and runs live in Firestore, not process memory, so restarts do not erase them.

Gold annotations reference chunk IDs. A new derived corpus or changed boundaries requires remapping supporting passages, human review and new run bindings; mark old corpus-bound annotations/evidence superseded for migration acceptance rather than treating them as validated for the new chain. Preserve prior identifiers/results for audit and rollback. Retrieval scoring consumes query, expected support IDs and ranked retrieved IDs/scores only; a changed answer digest cannot turn a perfect retrieval into a retrieval failure. Answer assessment separately consumes the generated answer, cited evidence and versioned human rubric. Operational failures are neither evidence refusals nor correct unanswerable outcomes: they fail operational-success and latency gates and do not enter refusal-correctness credit. Report eligibility requires current dataset/gold review and the exact candidate release manifest; old or incompatible results cannot authorize promotion. Existing cited/nonempty-answer evaluation proxies do not prove claim grounding or rubric quality; reviewed claim-level/citation/rubric assessments are required.

For R05, preserve FR-024's imported `supporting_passage` field on every record. For answerable items, bind it to one or more real relevant chunks; for an explicitly unanswerable item, retain the authored passage as review context but bind zero *relevant* chunk IDs and record the reviewer's corpus-scope refusal judgment. Store `corpus_version_id`, chunk content hashes, reviewer actor/time and binding version with the annotation. Reject a placeholder ID, cross-corpus ID, missing chunk or changed hash at gold approval. `scripts/remap_gold_annotations.py` remains an offline proposal source until its output is submitted through this authenticated, validated path. A dataset may stay exploratory while bindings or reviews are incomplete; no partial binding can become release evidence.

For R06, each pinned run item has separate `retrieval_status` and ranked chunk IDs, `generation_status` and typed outcome/error, and an `assessment_status` (`pending`, `reviewed`, `inapplicable`). Retrieval hit@5 is computed from answerable gold IDs even if generation fails or the answer changes. A retrieval error counts as operational failure and cannot be called a successful retrieval. For an unanswerable case, refusal correctness is applicable only after retrieval completes and the policy deliberately returns evidence refusal. A generated answer for an evaluator-authored question may be held in restricted `EvaluationItemOutput` so the reviewer can assess the exact candidate output; `RunItemAssessment` binds its digest, run/item/candidate/scorer versions, claim support, citation support and rubric result. This evaluator-only record is never populated from production user interactions. A changed output requires a new assessment. Any missing assessment or operational error prevents release eligibility, rather than shrinking denominators to make a gate pass.

### 7.3 Retention and recovery

Firestore application and vector data is backed up daily with at most 30 retained copies. A restore exercise must recover accounts, configuration, aggregate usage, evaluation and release decisions within 24 hours. The corpus index may instead be deterministically rebuilt from Cloud Storage. The current unconditional 30-day GCS source deletion must be replaced: active and retained rollback release references protect their exact object generations until the release/index recovery window closes. A dry-run garbage collector may delete only unreferenced generations after verifying at least one rebuild path remains. Account and evaluation-result retention is sponsor-controlled. Raw candidate outputs from evaluator-authored questions are provisionally deleted when the run is finalized or after 30 days, whichever comes first; digests and review results persist for audit (A-21). Safe operational metadata is provisionally retained for 30 days. Secrets remain in Secret Manager; release manifests store secret resource/version references and digests, never secret values or Terraform state copies of them.

## 8. Interfaces & Integrations

The browser uses Firebase Authentication for registration, email verification, sign-in, sign-out, and password recovery. It calls the backend through same-origin Firebase Hosting routing to `/api/**`, sending a Firebase identity token. The infrastructure endpoint may accept requests at the Cloud Run edge, but every protected operation requires application-level token, approval, and role validation.

The backend API exposes logical contracts for registration status, current user, question answering, quota status, user administration, configuration, aggregate metrics, JSON evaluation import, active dataset discovery and review, evaluation initiation/status/reports, and release decisions. Import accepts an administrator-authenticated JSON upload with bounded size and item count and returns the generation ID, submitted/imported/skipped counts, and indexed validation errors. Active-dataset lookup returns the current generation and review counts. Evaluation launch takes optional subset item IDs; the backend supplies the active dataset ID for a full run. Reports include `exploratory` or `release_evidence`, dataset generation, gold count, and versioned metrics. The answer response remains typed JSON with outcome, answer text, synthesis flag, citations, ephemeral trace and quota status. Evidence refusals remain successful request outcomes; operational failures retain a safe error shape but return a non-2xx HTTP status. This deliberate wire-contract correction requires client, probe and monitoring tests.

The target admin API extends the existing evaluation routes with `PUT /api/admin/evaluation-datasets/{generation_id}/items/{item_id}/binding` and `PUT /api/admin/evaluations/{run_id}/items/{item_id}/assessment`. The first accepts a candidate corpus binding, expected-refusal flag and reviewed chunk IDs; the server resolves those IDs and content hashes before changing approval state. The second accepts an exact output digest and human rubric/claim/citation decisions for one run item; the server checks the pinned candidate, scorer version and digest before finalizing. Both require admin identity, record actor/time, reject stale generations and are idempotent for identical submissions. Endpoint names are proposed targets; the request/response schemas and browser client must be versioned together. The current import and status-only review routes remain valid for exploratory use.

`POST /api/questions` has a versioned outcome contract: `answer` and `qualified` are successful cited responses; `refusal` means retrieval completed and evidence was absent; `operational_error` means a retrieval, provider, storage, validation or deadline failure. Only the latter returns non-2xx, with safe `ApiError.code`, retryability and available request-scoped trace. The browser, telemetry, evaluator and `scripts/run_performance_probe.py` classify by typed outcome and error, not just HTTP 200. Every displayed citation includes server-owned page/section and a bounded excerpt span from the retrieved chunk, plus a claim association. Invalid model IDs/spans are rejected uniformly across providers.

The backend and worker use the same native LangChain Embeddings configuration for Vertex AI workload-identity calls. `embed_documents` uses the document retrieval task; `embed_query` uses the query task. Native vector-store writes own embedding/persistence. Retrieval calls a score-returning library path with the corpus filter applied before nearest-neighbor selection, cosine distance and explicit `k=5`. Preserve `similarity = 1 - distance`; do not substitute rank-derived scores or library relevance normalization. Do not increase candidate count silently or filter other versions only after top-k. Missing/non-finite scores cannot count as supporting evidence, and unexpected missing scores are an integration failure to catch before release.

The native LangChain chat integration sends the minimum ephemeral prompt and passages over HTTPS. It validates structured output, normalizes errors, applies bounded timeouts, and invokes fallback only for configured model-level unavailability, timeout, capacity, or rate-limit conditions. Authentication or policy failures are not blindly retried. For the approved OpenRouter configuration, both models use the same gateway; gateway-wide failure produces the existing clear service error. Preserve effective provider/model settings per environment. Library errors/messages are mapped through safe existing public contracts; provider response bodies are not logged.

`RuntimeSettings` is a single validated projection of environment-specific non-secret settings, provider/Secret Manager references, collection/schema and candidate release identity. The API and both job entrypoints consume it; no module silently falls back to a conflicting provider/model or index default. Startup validates local syntax, ranges and required presence without a network call. Readiness makes a bounded, cached dependency and selected-release check without billable model inference; it reports a failed status if the selected corpus/configuration is unusable and never exposes secret values. The exact readiness timeout/cache interval is a provisional operational setting (A-22) to be measured within NFR-001.

Library contracts and package releases are validated in the compatibility spike; no direct SDK/HTTP RAG bypass is retained as a compatibility workaround. Supporting references: [Firestore 0.5.0 metadata](https://pypi.org/pypi/langchain-google-firestore/0.5.0/json), [OpenRouter 0.2.9 metadata](https://pypi.org/pypi/langchain-openrouter/0.2.9/json), [Google GenAI 4.4.1 metadata](https://pypi.org/pypi/langchain-google-genai/4.4.1/json), [Firestore search implementation](https://github.com/googleapis/langchain-google-firestore-python/blob/main/src/langchain_google_firestore/vectorstores.py), [Firestore converter](https://github.com/googleapis/langchain-google-firestore-python/blob/main/src/langchain_google_firestore/document_converter.py), [Google embeddings integration](https://reference.langchain.com/python/langchain-google-genai/embeddings/GoogleGenerativeAIEmbeddings), [OpenRouter chat integration](https://docs.langchain.com/oss/python/integrations/chat/openrouter), and [route-specific structured output](https://openrouter.ai/docs/guides/features/structured-outputs). ## 9. Cross-Cutting Concerns

**Security and privacy (NFR-004–NFR-006, NFR-011, NFR-014).** HTTPS, Firebase credential ownership/throttling/reset, server-side approval/role/ownership checks, default-deny browser Firestore access, least-privilege API/worker/scheduler/build accounts, and external secret delivery remain mandatory. Quota and authorization run before billable RAG stages. Never persist production questions, prompts, passages, answers, model output or traces in databases, object storage, logs, analytics, backups or artifacts. Retain only allowlisted structured metadata on stdout: counts, outcome, duration, model/provider ID, usage/cost estimate, quota utilization, corpus/config versions and safe error class. Do not log exception representations or SDK/provider bodies containing content; verify adapter success/error paths under the shipped logging configuration.

Disable environment-driven LangSmith/LangChain tracing, debug/verbose content logging, persistent model caches, history/checkpoints and content-bearing callbacks. Reject caller-supplied callbacks/configuration that bypass the privacy boundary. A transitive LangSmith dependency does not authorize external tracing or another downstream recipient. Existing warning against confidential/personal input and sponsor review of hosted-provider terms remain unchanged. Evaluator-authored datasets/results have the distinct durable treatment in section 7.

For R16, test direct instructions in the question and indirect instructions embedded in retrieved passages, including requests to ignore corpus policy, fabricate citations or reveal secrets. The trusted system policy and untrusted content boundaries are defense layers, while authorization stays in the API/retrieval data path. For R17, exact span membership and source lineage are deterministic checks; semantic entailment is measured with reviewed evaluator-authored cases. Reject or safely fail candidates with unknown IDs, missing claim links or altered excerpts. A valid citation ID alone never satisfies SM-02 or SM-03.

**Performance and concurrency (SM-06, NFR-001–NFR-002).** At least 95% of complete browser responses with citations must finish within 15 seconds under three-user normal load. The numerator requires the expected functional outcome and no operational error; HTTP 2xx alone is insufficient. Report operational failures and evidence refusals in separate denominators. Initial external Cloud Run settings remain min instances zero, max two, concurrency eight, one vCPU and 512 MiB, subject to measurement and the cost ceiling. Use native async embedding/chat/store interfaces where verified; run unavoidable synchronous Firestore work in a bounded executor off the event loop, with underlying RPC timeouts. Cancelling a thread wait does not prove cancellation of its network work. Verify three-user isolation, no shared mutable corpus filters, cold starts and graceful shutdown.

Adopt a provisional 14-second backend request deadline leaving approximately one second for browser/network overhead (A-15); measure and adjust within the unchanged 15-second target. Initial stage ceilings are 0.5 seconds auth/quota, 2 seconds query embedding, 1.5 seconds retrieval/prompt, 8 seconds generation shared by primary and eligible fallback, and 1 second validation/serialization, leaving one second backend contingency. Reserve approximately five seconds primary and up to three seconds fallback within the shared generation ceiling; actual attempts receive only remaining time. Unused stage time does not expand the whole-request ceiling. Provider/RPC timeouts, retry counts, job timeouts and resource limits stay externally configured. These are proposed budgets, not measured results: reconcile the current 16-second generation and 28-second request defaults in factories/Terraform/delivery before promotion, and prove the representative fallback mix meets the BRD. An operational timeout does not count as a successful complete answer.

Trace retrieval/generation/total timing consistently. Existing policy `total_ms` begins after retrieval; migrated total timing must include the full backend path, with separate browser/network end-to-end measurement for the release gate. Preserve existing field names and document measurement semantics; no hidden LangChain tracing is needed.

**Retrieval and answer quality (SM-01–SM-05, FR-007–FR-012).** Fix embedding dimensions/tasks and cosine distance per corpus version; use word-counted 700-word chunks/70-word overlap bounded to each PDF page, then subdivide any chunk that exceeds the serving excerpt limit before embedding. LangChain splitting may still change boundaries: compare real pages, preserve normalization/provenance, create a new derived corpus and review support changes. Preserve carried section recovery and the existing `Unclassified` fallback pending provenance review. Structural completeness, filtered vector readiness and measured gold retrieval quality are three distinct gates.

Evidence accepts only finite scores within the current supported range up to 1. Rank descending score, then ascending chunk ID for ties, cap at five, and discard scores below 0.45. Top score ≥0.75 is strong; ≥0.45 and <0.75 is partial; no eligible score is absent. Partial forces qualified output; absent produces the existing refusal without any generation call. Use exact `1-cosine_distance` semantics, without clamping/renormalization or invented rank scores. Test below/at/above thresholds, missing/non-finite/out-of-range scores, ties and mixed corpus versions.

Those existing 0.75/0.45 values are provisional, not a proven corpus calibration (R14). Freeze an evaluator-reviewed answerable/unanswerable dataset before tuning, separate tuning and held-out slices, and record threshold choice, false-refusal rate, unsupported-answer rate and hit@5 on held-out cases. The release gate retains SM-01 ≥90% for answerable gold items; recall@5, MRR, nDCG and category/section slices diagnose ranking. R15 compares a versioned dense baseline with lexical fusion and optional reranking on the same held-out cases. The provisional adoption target is at least five percentage points more hit@5 on a prespecified held-out terminology/numbered-section slice of at least 40 cases, no overall hit@5 loss, and no violation of SM-02, SM-05, SM-06, NFR-003 or privacy (A-20). If the slice is too small or the target fails, retain dense-only and record the result. Fusion scores are not cosine similarities: evidence thresholds must be calibrated to a strategy-specific score or applied only to a preserved dense score, never reused blindly.

Citations are reconstructed from retrieved authoritative page/section/excerpt records; schema parsing and citation membership alone do not prove every claim's support. Require reviewed relevant-passage retrieval ≥90%, grounded factual claims ≥95%, citation correctness ≥95%, answer rubric quality ≥85%, and correct refusal ≥95% on applicable gold cases. Retrieval hit uses ranked IDs before answer assessment; changed answer punctuation cannot change that score. Refusal correctness applies only to completed evidence-based refusals. Operational failures fail a separate gate and receive no refusal credit. Release requires 30–50 approved gold items with current candidate bindings and explicit report eligibility. Changed outputs/support receive human adjudication. Existing cited-answer/nonempty-answer evaluator proxies cannot by themselves establish semantic BRD gates.

**Reliability and recovery (BPR-006, NFR-009–NFR-010, NFR-013, NFR-015–NFR-017).** Availability remains best effort. Bound retries with backoff/jitter for safe reads/embeddings and idempotent explicit-ID indexing; user POSTs and quota reservation are not blindly retried. Accepted requests consume quota even on downstream failure. Model fallback is restricted to the existing eligible normalized errors and shared deadline; gateway failure yields a safe operational response. Do not imply unsupported content was successfully answered. Preserve any circuit-breaker policy and avoid adding implicit library retries.

Dataset import retains staged durable writes, transactional generation switching and failure isolation. Corpus ingestion separately requires persisted completeness and a candidate-filtered vector probe; publication requires a durable approved release decision and compare-and-set switch of the serving release. Roll back the serving image/configuration, collection/schema/index and corpus binding together; a pointer to v2 data is not a valid rollback for a v1 reader. Retain previous valid resources and exact source generations until promotion and rollback checks pass. Daily backups retain at most 30 copies; restore accounts/configuration/usage/evaluation/release decisions within 24 hours and prove corpus rebuild from immutable source.

**Observability and cost (SM-08, NFR-003, NFR-011).** Dashboards retain safe counts, stage/end-to-end latency, normalized errors, fallback rate, quota use, provider usage/cost, active corpus/configuration, ingestion/evaluation/backup status and infrastructure indicators. Alerts cover repeated failures, quota/cost forecasts, latency regression, backup/ingestion failure and retrieval below 90%. Diagnose content-dependent issues using authored test questions and live request traces. Forecast re-embedding, temporary duplicate vectors/indexes, artifact storage and larger dependency cold-start/memory cost before promotion. GCP infrastructure stays ≤€5/month plus separately approved provider hard cap; free/paid routes both require quality/privacy/capacity evidence.

The shipped Uvicorn configuration must enable `dmbok_compass.telemetry` and emit structured, content-free JSON to stdout on success and operational failure. Include random request ID, stage durations, typed outcome/error code, release/corpus/prompt/policy/model IDs, attempts, actual token usage and estimated cost where available. Administrative release/ingestion actions use actor-linked audit records; production query content is never retained. Synthetic events must match Terraform log metric filters and deliver alerts in a preview environment before promotion. Both model routes enforce a versioned output-token cap; absence of usage metadata is reported as unknown, not zero cost.

For R21, container startup fails before receiving traffic if the required route credentials, secret references, collection, model, embedding, timing or output-limit configuration is missing or invalid. Liveness only checks that the process can respond; readiness checks the selected release/configuration and required dependency access within a bounded budget. Secret rotation creates a new pinned version and candidate/release configuration digest. A passing liveness response must never be used as evidence that RAG is ready or that a release is compatible.

**Accessibility and UI parity (NFR-007–NFR-008).** Preserve responsive desktop/mobile flows, keyboard operation, focus, labels, status announcements, contrast, quota/reset explanations and safe errors. Existing user/admin core-flow and accessibility checks run against the unchanged response schemas. LangChain internals do not enter product screens.

**Deployment and Twelve-Factor standards (MIG-04).** Keep one canonical repository and explicit environment/release branches or tags. Declare and lock the entire Python integration stack, transitive dependencies and any patched artifact/source/hash; install and package one canonical lock in the final image and CI. The current final image installs `requirements.lock` while candidate snapshot code expects `requirements-compat.lock`; resolve that mismatch without relying on an unpackaged filename. Do not depend on global packages. Existing frontend lock remains required. Separate immutable build, release configuration and runtime; promote the exact tested image digest and Firebase artifact after preview/zero-traffic validation and approved evidence. Externalize provider/model/output cap/endpoint, project/region, credentials, collection/schema, splitter/task/dimension settings, deadlines and batch/scaling limits; document validated defaults in `.env.example` and secret names without values. Backing services remain externally configured and replaceable behind native integration contracts.

The final image must contain the exact installed lock that `backend/app/rag.py:_dependency_lock_sha256` hashes; CI starts that image and creates a candidate snapshot before accepting its build. Delivery treats `promotable=false`, missing/stale evidence, a missing durable approval, or any manifest/artifact mismatch as a failing promotion check. The configured output-token limit and source-generation retention policy are release settings, not process-local defaults. Terraform source-object lifecycle rules must be compatible with references in active and rollback releases.

Requests stay stateless; durable state is service-owned. API binds its HTTP port, terminates gracefully and honors Cloud Run signals; jobs stop safely between idempotent batches and exit nonzero on failure. Development and production use structurally similar container/dependency/schema configurations. Maintenance/migration/evaluation use the application image and configuration family. Terraform remains infrastructure source of truth, with explicit target and legacy vector indexes during migration. CI validates contracts, relevant policy/integration/privacy/evaluation tests, dependency resolution/lock, container/dependency scans and Terraform. Architecture approval does not execute deployment or IAM changes.

The production-readiness review ran local tests and reproduced integration failures; it did not verify the shipped image, deployed release, real-corpus quality or live recovery. **Owner:** implementation owner. **Validation:** ordered exit gates in section 13 and candidate-specific production evidence.
12. **A-12 — Safe metadata retention.** Content-free logs/metrics retain a provisional 30 days; never include interaction content. **Owner:** administrator. **Validation:** infrastructure retention and privacy inspection.
13. **A-13 — Managed email.** Firebase verification/reset delivery remains acceptable for first release. **Owner:** sponsor. **Validation:** existing end-to-end identity/regression flows before onboarding.
14. **A-14 — LangChain integration boundary.** Sponsor agreement with the recommendation is interpreted as accepting application policy retention and a narrow, maintained Firestore LangChain integration patch only if no supported compatible score-returning release is available. This does not approve a backing-store change, unverified downgrade or resolver bypass. **Owner:** implementation owner/sponsor. **Validation:** compatibility spike records the selected integration/artifact, exact lock, score semantics, maintenance/upstream plan and any necessary revised decision. If this path fails, stop dependent implementation.
15. **A-15 — Deadline allocation.** Provisional 14-second backend ceiling, eight-second shared generation budget and five/three-second primary/fallback reservation leave browser/network margin under the unchanged 15-second target. **Owner:** implementation owner/evaluator. **Validation:** measure complete responses, cold starts and representative fallback mix at three users; adjust within the same target/cost ceiling without treating errors as successful answers.
16. **A-16 — Migration data boundary.** The configured `document_chunks_v2` collection with nested metadata and derived fingerprint remains the internal index. Native word-counted 700/70 splitting may produce chunks too long for the serving excerpt field; deterministic subdivision is part of the next corpus version. **Owner:** corpus owner/implementation owner. **Validation:** schema round trip, persisted completeness, vector probe, idempotent batches, gold remapping and coupled rollback.
17. **A-17 — Release authority.** Firestore is the durable release registry and decision store; the same approved manifest selects the serving corpus and deployment tuple. This extends existing release repositories and avoids a new service. **Owner:** sponsor/implementation owner. **Validation:** restart, concurrent publication, blocked-bundle and mismatched-artifact tests; exact release rollback drill.
18. **A-18 — Output cap.** A product-specific output-token ceiling is selected from a measured answer-length distribution and is supported by both approved model routes; no numeric cap is asserted before route validation. **Owner:** sponsor/evaluator. **Validation:** route-level cap probe, completeness rubric, p95 latency and actual token/cost reports at three users.
19. **A-19 — Source retention.** Active and one validated rollback release remain recoverable; additional history retention is bounded by sponsor-approved cost and recovery policy. **Owner:** sponsor/administrator. **Validation:** reference inventory, lifecycle dry-run, restore/rebuild drill and budget review before automatic cleanup.
20. **A-20 — Optional lexical strategy.** A one-PDF, immutable lexical index artifact can fit the approved Cloud Run memory, cold-start and cost budgets. The provisional adoption target is at least five percentage points more hit@5 on a prespecified held-out terminology/numbered-section slice of at least 40 cases, with no overall hit@5 loss or regression against SM-02, SM-05, SM-06, NFR-003 and privacy. This is an experiment, not an approved serving strategy. **Owner:** retrieval/evaluator owner. **Validation:** build from the pinned chunk set, measure artifact size/load time and held-out quality/p95/cost before enabling R15; retain dense-only if it fails.
21. **A-21 — Evaluator-output retention.** Candidate outputs generated only from administrator-authored evaluation questions may be stored in admin-restricted Firestore for exact-output human review; they are not production user interactions. Provisionally delete raw output at run finalization or 30 days after generation, whichever occurs first, and keep only the digest and assessment afterward. This duration is not specified in the BRD. **Owner:** sponsor/evaluator. **Validation:** approve the policy and negative access/deletion tests before release; if disallowed, replace it with a review session that preserves the exact output until assessment without changing its digest.
22. **A-22 — Readiness probe budget.** Start with a two-second maximum dependency check and a short cached result, with the exact interval chosen from load testing. This is a provisional operational target, not an observed current capability. **Owner:** platform owner. **Validation:** failed-config, failed-store, cold-start and three-user probe tests under NFR-001; adjust without turning liveness into readiness.

The selected nine risks above are current implementation risks or observed design gaps, not hypothetical migration concerns. Other listed gates block promotion/release until candidate evidence or an existing sponsor risk decision is recorded; design approval itself does not assert they passed.

## 13. Notes for the Orchestrator

Scope of this revision is R04, R05, R06, R14, R15, R16, R17, R18 and R21 within the existing modular monolith and jobs. Freeze five minimal shared contracts first: `CandidateIdentity` (image/installed lock/corpus/config/scorer), `RetrievalResult` (ordered IDs/scores/provenance/strategy), `EvaluationCase`/`RunItemResult` (gold binding and independent stage statuses), `AnswerOutcome`/`CitationEvidence` (typed outcome and claim/span/source links), and `RuntimeSettings` (validated configuration and secret references). Each workstream can use contract fixtures and ship behind a disabled or compatible path; the integration gate, not another workstream's internal implementation, determines production adoption.

| Workstream | Independently reviewable change and exit evidence | Integration/adoption gate | Complexity |
|---|---|---|---|
| R21 | Central settings/startup validation, pinned secret references, separate bounded liveness/readiness; invalid config and unavailable selected release fail readiness | Exact release identity and deployed probe behavior must agree with existing R03/release controls | M |
| R04 | Final image contains installed `requirements.lock`; API/job candidate snapshot smoke hashes that file and records artifact identity | Delivery compares snapshot digest to immutable candidate/release manifest | S |
| R05 | Admin import/remap/binding and exact run-item review; placeholders and wrong-corpus IDs cannot become approved gold | 30–50 current, candidate-bound approved cases flow through real evaluation and release gate | M |
| R06 | Retrieval-only scorer and separate answer/refusal/operational statuses with adversarial scorer fixtures | R05's authored gold and R18's typed outcomes exercise the final evaluator; neither is needed to implement its scorer | M |

R04, R06, R16, R18 and R21 can start immediately using frozen fixture contracts. R05 and R14 can proceed in parallel; R15 can be built as an experiment, but its adoption waits for R14's measured baseline. R16 and R17 share the evidence shape, not a coding dependency. R05's authoring UI is not a prerequisite for R06 unit correctness; the real-data integration test joins them. R21's settings module is not a prerequisite for R04's image smoke, though both must identify the same candidate at release.

These are target work items, not completed fixes. Likely touchpoints are `backend/Dockerfile`, `backend/app/rag.py`, `backend/app/api/evaluation_datasets.py`, `backend/app/evaluation/{generations,worker,assessments}.py`, `backend/app/contracts/api.py`, `backend/app/retrieval/{search,evidence}.py`, `backend/app/answering/{pipeline,citations}.py`, `backend/app/{main,lifecycle}.py`, `web/src/questions/QuestionPanel.tsx`, `web/src/admin/evaluation/EvaluationPanel.tsx`, `scripts/run_performance_probe.py`, `infra/terraform/delivery.tf`, `.github/workflows/{quality,delivery}.yml`, and focused behavioral/integration tests. Reuse existing routes, repositories and jobs; new data types live inside those boundaries.

Freeze import bounds/categories, citation authority, embedding tasks/dimensions, metadata/index layout, annotation/report eligibility and privacy controls. Version the changed HTTP outcome, citation and release manifest contracts. Only candidate-specific passing evidence supports promotion; old reports and coarse proxies are insufficient. Existing publisher/provider risk decisions, model/privacy/budget approval and release controls remain binding.
